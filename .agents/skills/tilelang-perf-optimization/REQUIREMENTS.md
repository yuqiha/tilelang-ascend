# TileLang 性能调优 Skill 需求改进文档

## 1. 背景

`tilelang-perf-optimization` Skill 在实际运行中存在三个核心问题，导致优化过程不可控、精度问题难定位、文档形同虚设。本文档逐一描述问题现状、根因分析和改进需求。

---

## 2. Skill 缺陷分析

### 2.1 现有整体结构

```
Step 1: 精度校验（强制前置）
  → Step 2: 性能数据采集
  → Step 3: 算子类型判断
  → Step 4: 优化实施（无结构化流程）
  → Step 5: 精度再验证
  → Step 6: 效果验证
```

### 2.2 缺陷与问题对应关系

#### 缺陷 A：无优化点识别和排序机制 → 导致问题 1（乱序实施）

**现有 Step 4 的原文**

Step 4 仅给出一个优化方向表格：

| 优化方向 | 说明 | 典型手段 |
|---------|------|---------|
| pass_configs 调优 | 调整编译器 pass 行为 | 关闭自动同步、关闭内存规划 |
| 核内优化 | 提升单核内指令并行度 | Double Buffer、L1 常驻、指令向量化、Split-K pipelined GEMM |
| ... | ... | ... |

**缺陷分析**

| 缺失项 | 后果 |
|--------|------|
| 无优化点识别步骤 | Agent 不会系统性地阅读 `optimization-guide.md`，而是凭自身知识"想到什么做什么" |
| 无 ORDER-PLAN | 没有实施顺序的概念，Agent 随意选择优化点，可能先做 Double Buffer 再做 Split-K（顺序颠倒） |
| 无依赖分析 | 不知道 Split-K 是 Double Buffer 的前置条件，导致 Double Buffer 实施时 K 维未切分，流水无法生效 |
| 无适用性判断 | 不会逐条评估每个优化点是否适用于当前算子，可能实施不适用的优化（如对纯 AIV 算子做 Split-K） |

#### 缺陷 B：无逐项实施和门禁机制 → 导致问题 2（合并实施）

**现有核心约束的原文**

```
- **迭代验证**：每次只修改一个参数/配置，修改后立即验证，性能回退则回退
```

**缺陷分析**

| 缺失项 | 后果 |
|--------|------|
| "每次只修改一个参数"仅为一句话约束 | 没有结构化流程确保执行，Agent 在一次 Edit 中同时改 Double Buffer + Fixed Core + pass_configs |
| 无 `[SELF-CHECK]` 日志 | 没有要求 Agent 声明本次 Edit 只涉及哪个优化点，无法事后审计 |
| 无 `[SCOPE]` 声明 | 没有要求 Agent 声明修改范围，无法校验是否超出单优化点边界 |
| 无状态追踪表 | 没有记录哪些优化点已完成/进行中/待做，Agent 在长上下文中容易丢失进度 |
| Step 4 无子步骤 | 没有 Read → Edit → Verify 的强制顺序，Agent 可能跳过验证直接做下一个 |

#### 缺陷 C：无强制文档阅读机制 → 导致问题 3（不读 reference）

**现有文档引用的原文**

```
根据算子类型选择优化手段（详见 [optimization-guide](references/optimization-guide.md)）
```

以及：

```
- 若正在生成、改写或评审 kernel，先阅读 [performance-antipatterns](references/performance-antipatterns.md)
```

**缺陷分析**

| 缺失项 | 后果 |
|--------|------|
| 文档引用为"详见"而非"必须先读" | Agent 将其视为可选参考，而非强制前置步骤 |
| 无行号/章节定位 | 只给了文件链接，未指定具体章节，Agent 可能只读标题就跳过 |
| 无 `[IMPL-#N]` 日志 | 没有要求 Agent 记录"已读哪个文件的哪些行"，无法验证是否真的读过 |
| 无必读文档清单 | 每个优化点需要读哪些文档完全由 Agent 自行判断，经常遗漏关键文档（如 `sync-primitives-guide.md`） |
| 无强制自检项 | Double Buffer 的同步模式选择等关键决策点没有强制 Agent 回答自检问题 |
| `optimization-guide.md` 长达 963 行 | Agent 在有限上下文窗口中难以完整阅读，需要精确的章节指引 |

### 2.3 缺陷总结

```
现有 SKILL.md
├── 无优化点识别步骤 ──────────→ Agent 凭直觉选优化点 ──→ 乱序实施
├── "每次只改一个"仅一句话 ───→ Agent 合并多个修改 ──────→ 精度难定位
├── "详见文档"非强制 ─────────→ Agent 跳过文档阅读 ──────→ 重复犯错
└── 无结构化流程/日志/门禁 ───→ 以上三个问题无法被发现和纠正
```

## 3. 问题清单

### 问题 1：优化点不按顺序实施

**现状描述**

SKILL.md 中没有 ORDER-PLAN 概念，也没有优化点识别步骤。Agent 在 Step 4 优化实施时凭直觉选择优化点，随意打乱实施顺序。

**典型表现**

- Agent 先做 Double Buffer 再做 Split-K（顺序颠倒，Split-K 是 Double Buffer 的前置条件）
- 跳过某些优化点，直接实施后面的优化点
- 不会逐条评估每个优化点是否适用于当前算子

**影响**

- 后续优化点依赖前置优化点的 layout/buffer 变更，乱序实施导致编译错误或精度异常
- 优化效果无法归因，性能数据不可信

**根因分析**

| 根因 | 说明 |
|------|------|
| 无 ORDER-PLAN | Step 4 仅给出优化方向表格，没有实施顺序的概念 |
| 无依赖分析 | 不知道优化点之间存在前置依赖关系 |
| 无状态追踪 | 没有持久化记录哪些优化点已完成，Agent 在长上下文中容易丢失顺序信息 |

---

### 问题 2：多个优化点合并实施

**现状描述**

核心约束中仅用一句话"每次只修改一个参数/配置"约束，无任何结构化机制确保执行。Agent 在实际执行时，经常在一次 Edit 中同时应用 2-3 个优化点的修改，然后才运行验证。

**典型表现**

- 一次 Edit 同时修改了 Double Buffer 和 Fixed Core 相关代码
- 验证失败时无法判断是哪个优化点引入的问题
- 回滚时只能整体回滚，无法精确定位

**影响**

- 精度失败时无法定位到具体优化点，调试成本大幅增加
- 性能提升无法归因到单个优化点，优化报告数据失真
- 违反"精度优先"原则，多个变更叠加可能引入难以排查的精度劣化

**根因分析**

| 根因 | 说明 |
|------|------|
| 仅文字约束 | "每次只修改一个参数"仅为一句话，没有结构化流程确保执行 |
| 无 SELF-CHECK 日志 | 没有要求 Agent 声明本次 Edit 只涉及哪个优化点，无法事后审计 |
| 无 SCOPE 声明 | 没有要求 Agent 声明修改范围，无法校验是否超出单优化点边界 |
| 缺少 diff 范围约束 | 未要求 Agent 在 Edit 前声明本次修改的代码范围，无法事后校验 |

---

### 问题 3：实施优化点前不读 reference 文档

**现状描述**

文档引用为"详见"式建议，无强制阅读机制。Agent 在实际执行时经常跳过文档阅读，直接基于自身理解编写代码，导致重复犯 reference 文档中已有明确说明的错误。

**典型表现**

- Double Buffer 实施时未读 `sync-primitives-guide.md`，选错同步模式（如该用 `AUTO_SYNC=False` 时用了 `True`）
- 修改 `pass_configs` 时未读 `tilelang-expert-to-developer` 文档，配置项写错
- 优化指南中明确标注的"铁律"、"自检"项被忽略

**影响**

- 重复犯已有文档明确规避的错误，浪费迭代轮次
- 优化效果不达预期（如 AUTO_SYNC 未关闭导致 Double Buffer 形同虚设）
- 增加不必要的调试时间

**根因分析**

| 根因 | 说明 |
|------|------|
| 文档引用为建议非强制 | Agent 将"详见"视为可选参考，而非强制前置步骤 |
| 无行号/章节定位 | 只给了文件链接，未指定具体章节，Agent 可能只读标题就跳过 |
| 无必读文档清单 | 每个优化点需要读哪些文档完全由 Agent 自行判断，经常遗漏关键文档 |
| 无强制自检项 | Double Buffer 的同步模式选择等关键决策点没有强制 Agent 回答自检问题 |
| 文档过长 | `optimization-guide.md` 有 963 行，Agent 在有限上下文窗口中难以完整阅读 |

## 4. 改进需求

### 需求 1：强制顺序执行机制

**目标**：确保 Agent 严格按照分析出的顺序实施优化点。

**需求描述**

| 编号 | 需求项 | 优先级 |
|------|--------|--------|
| R1.1 | 新增 **优化点识别步骤**（独立于优化实施步骤，禁止合并），要求 Agent 系统性阅读 `optimization-guide.md` 对应章节 + `performance-antipatterns.md`，逐条标注每个优化点的适用/不适用 + 原因 + 参考文件行号 | P0 |
| R1.2 | 新增 **`[ORDER-PLAN]`** 输出，分析优化点之间的依赖关系，排出实施顺序链。依赖分析三条规则：(1) 布局依赖：改变 layout 的优化排在依赖此 layout 的优化之前；(2) 数量依赖：涉及预算的优化排在改变 buffer 数量的优化之后；(3) 配置依赖：涉及 pass_configs 的优化在相关功能实施后才改动 | P0 |
| R1.3 | 在 `optimization_log.md` 中维护一个 **状态追踪表**，记录每个优化点的状态（pending/in_progress/done/skipped），每次实施前更新 | P0 |
| R1.4 | 新增 **`[ORDER-CHECK]`** 门禁，必须显式引用状态追踪表，校验前置依赖项的状态为 `done`，否则输出 `[BLOCKED]` 并禁止实施 | P0 |
| R1.5 | 禁止跳序：如果 ORDER-PLAN 中 #N 状态为 `pending`，禁止实施 #N+1 及后续优化点 | P0 |
| R1.6 | 如果某个优化点不适用需要跳过，必须在状态表中标注 `skipped` 并写明原因，然后才能继续下一个 | P1 |

**建议的 SKILL.md 修改方向**

新增独立的优化点识别步骤（禁止与实施步骤合并），并在实施步骤开头增加状态追踪表：

```
### Step 3: 识别优化点（强制，禁止与 Step 4 合并）

Part A 优化点清单：
[#1] [名称]（参考: optimization-guide.md L445-L650 §2.13）：[适用/不适用] — [原因]

Part B [ORDER-PLAN]：
1. [#N] [名称] — 前置依赖: [无] — 理由: [...]
2. [#M] [名称] — 前置依赖: [#N] — 理由: [...]

### Step 4: 逐项实施

状态追踪表（每次实施前必须更新）：
| # | 优化点 | 状态 | 精度 | 性能(us) | 备注 |
|---|--------|------|------|----------|------|
| 1 | Split-K | pending | - | - | |
| 2 | Double Buffer | pending | - | - | 前置: #1 |
| 3 | Fixed Core | pending | - | - | 前置: #2 |

[ORDER-CHECK] 准备实施: [#N] | 前置依赖检查: [#1=done ✅] | 结论: ✅ 可实施
[ORDER-CHECK] 准备实施: [#N] | 前置依赖检查: [#1=pending ❌] | 结论: [BLOCKED] 禁止实施
```

---

### 需求 2：强制单点实施机制

**目标**：确保每次 Edit 只修改一个优化点，验证通过后才进行下一个。

**需求描述**

| 编号 | 需求项 | 优先级 |
|------|--------|--------|
| R2.1 | 将"逐项实施"提升为 **核心约束** 第一条，明确"每次 Edit 只改一个优化点，改完立即验证" | P0 |
| R2.2 | 新增 **6 子步骤流程**：`ORDER-CHECK → Read 文档 → Edit 代码 → msprof op 验证 → 记录结果 → (失败) 重读文档修复`，并设置门禁：`[ORDER-CHECK]` 未写禁止 Read；`[IMPL-#N]` 未写禁止 Edit；`[RESULT-#N]` 未写禁止下一个 | P0 |
| R2.3 | 每次 Edit 前必须声明 `[SCOPE]` — 本次修改涉及的代码范围（文件名 + 函数名/行号区间） | P0 |
| R2.4 | `[SCOPE]` 声明后，Edit 操作不得超出声明范围。如果超出，必须在日志中说明原因并重新声明 | P0 |
| R2.5 | 新增 `[SELF-CHECK]` 日志，要求 Agent 声明本次 Edit 只涉及哪个优化点 | P0 |
| R2.6 | 每次 Edit 后必须立即运行 `msprof op` 验证，验证结果记录到状态追踪表后才能开始下一个优化点 | P0 |
| R2.7 | `pass_configs` 修改不作为独立优化点，是伴随修改，但必须在关联的功能优化点的 `[SCOPE]` 中明确列出 | P1 |
| R2.8 | 禁止"顺便修改"：如果 Edit 过程中发现需要修改其他优化点的代码，必须记录为 `[DEFER]` 并在对应优化点实施时处理 | P1 |

**建议的 SKILL.md 修改方向**

```
[ORDER-CHECK] 准备实施: [#N] [名称] | 前置依赖: [#1 ✅ / #2 ❌] | 结论: [✅/❌]
[IMPL-#N] 已阅读 <文件> L行号（§X.X），关键约束: ...
[SCOPE] 本次修改范围: examples/rope/rope.py, kernel() 函数, L45-L80
[SELF-CHECK] 本次 Edit 只涉及 [#N]
[RESULT-#N] 优化点: [名称] | 精度: [pass/fail] | 性能: [X us] | 对比: [+/-X%]
→ 状态追踪表 #N 更新为 done
→ 开始下一个优化点
```

### 需求 3：强制文档阅读机制

**目标**：确保 Agent 在实施每个优化点前，必须阅读对应的 reference 文档章节。

**需求描述**

| 编号 | 需求项 | 优先级 |
|------|--------|--------|
| R3.1 | 在 6 子步骤中将 **`A: Read 文档`** 设为 `B: Edit 代码` 的强制前置步骤 | P0 |
| R3.2 | 新增 `[IMPL-#N]` 日志，必须包含：实际读取的文件路径、行号区间、章节标题，以及提取出的关键约束 | P0 |
| R3.3 | 如果 `[IMPL-#N]` 日志缺失，禁止进入 Edit 步骤（通过门禁机制实现） | P0 |
| R3.4 | 为每个优化点建立 **必读文档清单**，在优化点识别步骤中一并输出 | P0 |
| R3.5 | 在 `optimization-guide.md` 的每个优化章节末尾增加 **"实施前必读"** 小节，明确列出该优化点需要阅读的所有文档和章节 | P1 |
| R3.6 | 对于高频出错的优化点（如 Double Buffer 同步模式选择），增加 **"强制自检项"**，Agent 必须在日志中逐项回答 | P1 |
| R3.7 | 新增 **Host 轻量化约束**：禁止 host 侧全量数据搬运（`F.pad`、`.contiguous()`、`.to(dtype)` 等），必须移入 kernel | P1 |

**建议的 SKILL.md 修改方向**

在优化点清单中增加必读文档列：

```
[#2] [Double Buffer]（参考: optimization-guide.md L77-L179 §2.2）：[适用]
     必读文档:
       - optimization-guide.md §2.2.0 同步模式决策表
       - sync-primitives-guide.md §1-§3
       - performance-antipatterns.md "纯 AIV memory bound 算子" 章节
     强制自检:
       - Q1: 循环内有 MTE3？ → [是/否]
       - Q2: 有跨迭代累加器？ → [是/否]
       - Q3: 选同步方式 → [AUTO_SYNC=True/False]，依据: [...]
```

在实施步骤的 `[IMPL-#N]` 日志中增加文档验证：

```
[IMPL-#2] 已阅读:
  - optimization-guide.md L77-L179 §2.2（Double Buffer 原理和示例）
  - optimization-guide.md L91-L110 §2.2.0（同步模式决策表，选择 AUTO_SYNC=False）

[DB-ANALYSIS] Q1: 循环内有 MTE3 → 是 | Q2: 无跨迭代累加器 → 否 | Q3: AUTO_SYNC=False，依据: 纯 AIV Vector 算子
```

## 6. 验收标准

| 验收项 | 通过条件 |
|--------|---------|
| 顺序执行 | 连续 3 次运行，优化点实施顺序与 ORDER-PLAN 完全一致 |
| 单点实施 | 连续 3 次运行，每次 Edit 只涉及一个优化点，验证通过后才继续 |
| 文档阅读 | 连续 3 次运行，每个优化点的 `[IMPL-#N]` 日志包含正确的文档引用和行号 |
| 精度可追溯 | 精度失败时，能在 1 步内定位到引入问题的优化点 |
| 日志完整性 | `optimization_log.md` 包含完整的状态追踪表、ORDER-CHECK、IMPL、RESULT 日志 |
